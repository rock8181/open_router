# 문서 검색 및 인덱싱 설계 문서

## 1. 개요

본 문서는 open_router 프로젝트의 `web_server/doc` 및 `study` 폴더 내 마크다운 문서들을 키워드로 검색할 수 있는 문서 검색 및 인덱싱 기능을 설계한다. 사용자는 웹 인터페이스를 통해 키워드를 입력하고 관련 문서를 조회할 수 있으며, 서버 측에서는 메모리 기반 인덱스를 구축하여 빠른 검색 응답을 제공한다.

## 2. 검색 방식

### 2.1 단순 full-text 검색

인덱스된 문서의 전체 내용(파일 내용)에서 사용자가 입력한 키워드와 일치하는 부분을 매칭한다. 정확한 단어 매칭뿐만 아니라 부분 문자열 매칭을 지원하여 사용자가 전체 단어를 입력하지 않아도 관련 문서를 찾을 수 있다.

### 2.2 제목 우선 가중치

검색 결과 순위를 결정할 때 제목(title)에 키워드가 매칭된 문서에 더 높은 가중치를 부여한다. 내용(content)에만 매칭된 문서보다 제목에 매칭된 문서를 상위에 노출하여 사용자가 원하는 문서를 빠르게 찾을 수 있도록 한다.

### 2.3 내용 부분 매칭

키워드가 문서 내용의 일부에 포함되어도 검색 결과에 포함된다. 예를 들어 "설계"라는 키워드를 입력하면 "설계 문서", "문서 설계" 등 키워드가 포함된 모든 내용을 검색 대상으로 한다.

### 2.4 스니펫 생성

검색 결과 각 항목에 대해 매칭 키워드 주변의 문장을 추출하여 스니펫(snippet)을 생성한다. 사용자가 검색 결과를 클릭하지 않아도 문서의 어떤 부분이 키워드와 관련이 있는지 직관적으로 알 수 있도록 한다.

## 3. 인덱스 전략

### 3.1 인덱스 구축 시점

서버 시작 시 또는 주기적으로(doc 및 study 폴더를 스캔하여 메모리 기반 인덱스를 구축한다. 인덱스는 서버 메모리上에 유지되며, 검색 요청 시 디스크 I/O 없이 빠르게 응답할 수 있다.

### 3.2 인덱스 항목 구조

각 문서에 대한 인덱스 항목은 다음과 같은 구조를 가진다:

```typescript
interface SearchIndexItem {
  filePath: string;      // 문서의 절대 경로 또는 상대 경로
  title: string;         // 문서 제목 (마크다운 H1 헤더 또는 파일명)
  content: string;       // 문서 전체 텍스트 내용
  modifiedAt: Date;      // 최종 수정 시간
  keywords: string[];    // 추출된 키워드 리스트 (토큰화된 단어들)
}
```

### 3.3 파일 변경 감지 및 인덱스 갱신

`fs.watch`를 사용하여 doc 및 study 폴더 내 파일 생성, 수정, 삭제 이벤트를 감지한다. 파일이 변경되면 해당 문서만 재스캔하여 인덱스를 갱신한다. `fs.watch`가 작동하지 않는 환경에서는 일정 간격(예: 30초)으로 폴링(polling)하여 변경 사항을 확인하는 폴백 방식을 사용한다.

### 3.4 마크다운 파싱

마크다운 문서에서 H1 헤더(`# 제목`)를 추출하여 제목(title)로 사용한다. H1이 없는 경우 파일명(확장자 제외)을 제목으로 사용한다. 마크다운 문법(`#`, `**`, `` ` `` 등)은 검색 인덱스 구축 시 제거하고 순수 텍스트만 인덱싱한다.

## 4. 검색 API

### 4.1 엔드포인트

```
GET /api/search?q=키워드&root=폴더명
```

### 4.2 요청 파라미터

| 파라미터 | 타입 | 필수 | 설명 |
|----------|------|------|------|
| q | string | 예 | 검색 키워드 |
| root | string | 아니오 | 검색 대상 폴더명 (doc 또는 study, 생략 시 전체 검색) |

### 4.3 응답 형식

```json
{
  "query": "검색 키워드",
  "total": 15,
  "results": [
    {
      "filePath": "doc/01_overview.md",
      "title": "개요",
      "snippet": "...키워드 주변 문장...",
      "score": 0.95,
      "matchedIn": ["title", "content"]
    }
  ]
}
```

### 4.4 결과 제한

검색 결과는 최대 20건까지 반환하며, 점수(score) 순으로 정렬된다. 각 결과에는 스니펫이 포함되어 사용자가 문서 내용을 미리 확인할 수 있다.

## 5. UI 검색

### 5.1 검색 바

웹 인터페이스 상단에 검색 바를 배치한다. 사용자가 키워드를 입력하면 실시간으로 검색 결과를 표시한다.

### 5.2 실시간 검색 (debounce 300ms)

사용자가 입력할 때마다 즉시 검색 API를 호출하지 않고, 입력 완료 후 300ms 정지 시점에 검색 요청을 전송하는 디바운스(debounce) 처리를 적용한다. 불필요한 API 호출을 줄이고 서버 부하를 경감한다.

### 5.3 결과 하이라이팅

검색 결과 목록과 스니펫에서 매칭된 키워드를 시각적으로 하이라이팅(강조 표시)한다. 사용자가 어떤 키워드로 문서가 매칭되었는지 쉽게 파악할 수 있다.

## 6. 한글 검색

### 6.1 한글 키워드 지원

한글 키워드로 검색할 수 있도록 한다. 한글은 음절 단위로 토큰화하지 않고, 입력된 문자열 그대로 부분 매칭을 수행한다.

### 6.2 대소문자 무시

검색 시 대소문자를 구분하지 않는다. 예를 들어 "Design", "design", "DESIGN" 모두 동일한 결과를 반환한다. 한글은 대소개념이 없으므로 영향이 없다.

## 7. 성능

### 7.1 메모리 인덱스 충분

문서 수가 적으므로(수십~수백 개) 메모리 기반 인덱스로 충분하다. 외부 데이터베이스(Elasticsearch, SQLite 등)를 도입할 필요 없이 서버 메모리에 인덱스를 유지하여 간단한 아키텍처를 구성한다.

### 7.2 검색 응답 시간

인덱스가 메모리에 있으므로 검색 요청은 밀리초 단위로 처리된다. 파일 스캔 및 인덱스 구축은 서버 시작 시 한 번만 수행되며, 이후 검색은 메모리 상에서 이루어져 지연이 거의 없다.

## 8. 구현 계획

1. doc 및 study 폴더 스캔 함수 구현
2. 마크다운 파싱 및 텍스트 추출 함수 구현
3. 메모리 인덱스 데이터 구조 및 구축 로직 구현
4. fs.watch 또는 폴링 기반 파일 변경 감지 구현
5. GET /api/search API 엔드포인트 구현
6. 프론트엔드 검색 바 UI 구현 (debounce 300ms, 하이라이팅)
7. 스니펫 생성 로직 구현
8. 검색 결과 정렬 및 가중치 적용 로직 구현

## 9. 참고사항

- 인덱스 구축 시 마크다운 문법 제거 후 순수 텍스트만 인덱싱한다.
- 검색 결과는 제목 매칭 우선, 내용 매칭 후순위로 정렬한다.
- 스니펫은 매칭 키워드 주변 ±50자程度를 추출한다.
- 검색 결과는 최대 20건으로 제한한다.
